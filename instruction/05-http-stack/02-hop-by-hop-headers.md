# Hop-by-Hop Headers

Some headers describe the connection between two adjacent hops, not the
end-to-end message. A proxy that forwards them is forwarding a statement
about a connection that no longer exists — which is a correctness bug, and
in the case of the framing headers, a security one.

## What to learn
### The set, and why each one is per-hop
`Connection`, `Keep-Alive`, `Transfer-Encoding`, `TE`, `Trailer`,
`Upgrade`, `Proxy-Authorization`, `Proxy-Authenticate`.

Each describes something about *this* link: how this connection is framed,
whether it stays open, what this hop is allowed to send, who authenticated
to this proxy. Your connection to the upstream has its own framing, its
own keep-alive state, its own upgrade status — so these must be
regenerated for that connection, never inherited from the inbound one.

### `Connection` also names additional headers
`Connection` is doubly special: beyond being hop-by-hop itself, it *names*
other headers to treat as hop-by-hop. A request carrying
`Connection: X-Foo, Keep-Alive` is saying "`X-Foo` is for you only" — so
you must remove `X-Foo` too, then remove `Connection` itself.

```rust
// strip the named headers first, then the standard hop-by-hop set
if let Some(conn) = req.headers().get(header::CONNECTION).cloned() {
    for name in conn.to_str().unwrap_or("").split(',') {
        req.headers_mut().remove(name.trim());
    }
}
for name in HOP_BY_HOP {          // Connection, Keep-Alive, TE, Trailer,
    req.headers_mut().remove(name); // Transfer-Encoding, Upgrade, Proxy-*
}
```

Gotcha: that mechanism is attacker-controlled. A client sending
`Connection: Authorization` convinces a naive proxy to strip a header a
downstream component depended on — or, in the reverse arrangement, to
strip a security header your own infrastructure adds. The defense is
ordering: strip hop-by-hop headers first, then apply your own trusted
headers (`07-security/01-auth.md`'s identity injection), so nothing the
client said can remove them.

Gotcha: the `Connection` value is a comma-separated list written by the
peer — cap how many entries you'll process and ignore malformed ones,
rather than looping over an attacker-sized list.

### Forwarding `Transfer-Encoding` is how you build a smuggling bug
Of the whole set, the framing headers are the dangerous ones. The framing
for your upstream connection must be **generated by you**, from the body
you are actually about to send — not copied from what arrived.

A proxy that forwards `Transfer-Encoding: chunked` unchanged while writing
a body it framed differently has manufactured a disagreement between its
own framing and what it told the upstream to expect. That is exactly the
desync in `07-security/05-request-smuggling.md`, self-inflicted.

The same applies when you change the body: compressing a response while
streaming (`05-http-stack/06-compression.md`) invalidates the inbound
`Content-Length`, and forwarding it anyway produces the same class of bug
from the opposite direction.

### `Upgrade` is hop-by-hop, and WebSockets need it anyway
`Connection: Upgrade` and `Upgrade: websocket` are per-hop by definition —
the client is upgrading *your* connection, and you separately upgrade your
connection to the upstream. So a correct implementation strips them and
then deliberately re-adds them for the upstream leg.

Gotcha: this is the most common way a working proxy loses WebSocket
support during a refactor — someone adds correct hop-by-hop stripping and
the upgrade path silently stops working, because nothing re-adds the
headers. `05-http-stack/09-websocket.md` covers the upgrade flow; the header
handling is a special case of this file.

### End-to-end headers you should still not blindly forward
Hop-by-hop is a spec concept; there's a second, larger set that is
end-to-end by spec but should not cross your trust boundary:
- **Identity headers** your infrastructure trusts (`X-User-Id`,
  `X-Auth-*`) — `07-security/01-auth.md`.
- **`X-Forwarded-For` / `Forwarded`** from untrusted peers —
  `07-security/08-ip-filtering.md`.
- **Anything you set yourself** downstream of this point, or a client can
  pre-set it and win.

All three have the same shape: a header is trusted because "the proxy sets
it", so a client that can set it impersonates the proxy. Strip them at the
same early point as the hop-by-hop set — one place, before any module
reads anything.

### Do it once, before anything reads headers
Put both strips in a single stage at the front of the pipeline
(`09-architecture/01-components.md`), before routing, auth, WAF, or logging.
A strip that happens inside the auth module doesn't protect routes
configured `Public`; a strip that happens after logging means forged
headers appear in your logs as though they were real.

## Practice
Build these in order.

1. In `labs/05-reverse-proxy`, implement hop-by-hop stripping including
   `Connection`-named headers, as one stage at the front of the pipeline.
   **Done when** a request with `Connection: X-Secret` and an `X-Secret`
   header reaches the upstream with neither.
2. Regenerate framing on forward. **Done when** the request your proxy
   emits carries `Content-Length`/`Transfer-Encoding` it computed from the
   body it is actually sending — verify by inspecting raw bytes, not by
   reading the code.
3. Try the stripping attack. **Done when** `Connection: Authorization`
   from a client does not remove the identity header your proxy adds,
   because yours is applied after stripping.
4. Add identity and forwarded-for stripping to the same stage. **Done
   when** a forged `X-User-Id` is gone on every path — including the
   `Public` route and the 404 path.
5. Re-add upgrade headers for the upstream leg. **Done when** a WebSocket
   still works end-to-end after step 1 — this is the regression that
   hop-by-hop stripping classically causes.
6. Fuzz the `Connection` header (`12-testing/02-fuzzing.md`) with many
   entries, empty entries, and malformed names. **Done when** none of it
   panics or causes unbounded work.
